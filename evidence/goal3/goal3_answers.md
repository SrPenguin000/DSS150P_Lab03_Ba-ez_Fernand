1. Which file format was smallest on your machine, and what encoding/compression characteristics help explain the result?
Parquet was by far the smallest at ~4.1 MB, compared to CSV (~14.9 MB) and JSONL (~28.2 MB). Parquet achieves this because it is a columnar format, meaning all values for a single column are stored adjacently. This homogeneous data allows for highly efficient type-specific compression (like dictionary encoding for repetitive text such as status, or delta/run-length encoding for timestamps and numbers). Additionally, we explicitly applied Snappy block compression during the write phase.

2. Which representation was fastest for a full dataset read? Does that imply it is best for every workload?
Parquet was the fastest for a full read (median ~0.0340 seconds), heavily outperforming JSONL (~0.4789s) and PostgreSQL (~0.3238s). However, this does not make Parquet universally superior. Parquet is heavily optimized for Online Analytical Processing (OLAP) and bulk reads. It is terrible for Online Transaction Processing (OLTP) workloads that require single-row inserts, updates, or deletions—a scenario where PostgreSQL thrives. CSV and JSONL also maintain an advantage in human-readability and ease of debugging.

3. How did filtered retrieval differ between Parquet and PostgreSQL? What additional PostgreSQL design (such as an index) could change the result?
Parquet completed the filtered retrieval (status = 'DELIVERED') extremely fast (~0.0226 seconds) because columnar engines can push the filter down to the file level, entirely skipping blocks of data where the dictionary indicates no 'DELIVERED' statuses exist. PostgreSQL took much longer (~0.1056 seconds) because, without an index on the status column, the database engine was forced to perform a full sequential scan of the entire table in memory. Creating a B-Tree index on curated.sales_order_lines(status) would allow PostgreSQL to look up the exact disk locations of the delivered orders instantly, drastically reducing query time.

4. Why is JSON Lines generally more pipeline-friendly than one giant JSON array for append/stream-oriented processing?
JSON Lines stores each record as a separate, self-contained JSON object separated by a newline character. This allows data pipelines to read, process, and write data line-by-line (streaming) without loading the entire dataset into memory. If the data were stored as one giant JSON array, a parser would have to read the entire file into memory to validate the array structure before processing, which causes out-of-memory (OOM) failures on large datasets. JSONL also allows you to simply append a new line to the end of a file, whereas a giant array requires manipulating the closing ] bracket.

5. What happens if a partition key has extremely high cardinality or poor query locality?
Partitioning by a high-cardinality column (like order_id or a very granular order_timestamp down to the second) creates the infamous "small files problem." Instead of a few large files, the system generates tens of thousands of tiny directories and files. This introduces massive metadata overhead, drastically slows down I/O because the OS has to constantly open and close file handlers, and defeats the purpose of block compression since each file is too small to compress effectively.
